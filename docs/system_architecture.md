# معمارية النظام — نظام ذكي لإدارة ومتابعة مشاريع البناء السكنية

**الإصدار:** 1.0 — 14 أكتوبر 2026
**الحالة:** مسودة للاعتماد. لم يُغيَّر أي كود أو مخطط بعد (انظر القسم 13).
**يرتبط بـ:** `graduation_project_master_reference.md` (النطاق والأولويات) و`schema.sql` (قاعدة البيانات).

---

## 1. الأهداف المعمارية

| الهدف | معناه عمليًا |
|---|---|
| **التقسيم (Modularity)** | كل ميزة كبيرة في وحدة مستقلة بحدود واضحة، يمكن بناؤها واختبارها وحذفها دون كسر غيرها. |
| **العزل (Isolation)** | عزل الكود بين الوحدات، وعزل بيانات كل مشروع عن غيره، وعزل الخدمات الخارجية (n8n، الذكاء الاصطناعي) خلف واجهات ضيقة. |
| **التوسع (Scalability)** | يبدأ بنشر واحد بسيط، ويمكن لاحقًا فصل أي وحدة إلى خدمة مستقلة دون إعادة كتابة. |
| **قابلية القطع** | أي ميزة يمكن إيقافها بمفتاح (feature flag) دون ترقيع، لتتوافق مع ترتيب القطع في القسم 8 من المرجع. |
| **الجدارة بالثقة** | الأرقام المالية والهندسية تُحسب في مكان واحد، ويمكن تتبع كل تعديل عليها. |

**ما ليس هدفًا:** لا نبني للملايين من المستخدمين. نبني حدودًا صحيحة تسمح بذلك لاحقًا، ولا ندفع ثمنه الآن.

## 2. القرار الأساسي: Modular Monolith وليس Microservices

**القرار:** تطبيق واحد قابل للنشر (Next.js + TypeScript) مقسّم داخليًا إلى وحدات معزولة، مع خدمتين طرفيتين فقط: n8n ومزود الذكاء الاصطناعي.

| الخيار | لماذا رُفض أو قُبل |
|---|---|
| Microservices من البداية | **مرفوض.** فريق من شخصين، تعقيد النشر والشبكة والمعاملات الموزعة سيستهلك وقت الميزات. لا حاجة قياسية تبرره. |
| Monolith عادي بلا حدود | **مرفوض.** يتحول بسرعة إلى كتلة مترابطة يصعب قطع جزء منها أو اختباره. |
| **Modular Monolith** | **مقبول.** يعطي فوائد العزل والتوسع دون كلفة التوزيع، وحدوده قابلة للفرض آليًا. |

**شرط نجاح هذا القرار:** أن تُفرض الحدود بأدوات (القسم 5)، لا بالنية الحسنة فقط. فالحدود غير المفروضة تتآكل خلال أسابيع.

## 3. الطبقات

```
واجهة المستخدم (UI)        ← صفحات ومكوّنات React، RTL، لا منطق أعمال
        │  تستدعي فقط
        ▼
طبقة التطبيق (Application) ← حالات الاستخدام (use cases)، الصلاحيات، المعاملات
        │  تستخدم
        ▼
النطاق (Domain)            ← قواعد وحسابات نقية بلا إدخال/إخراج (pure)
        ▲
        │  تنفّذ منافذ (ports) يعرّفها النطاق والتطبيق
البنية التحتية (Infra)     ← Supabase، التخزين، n8n، مزود الذكاء الاصطناعي، البريد
```

**قاعدة اتجاه الاعتماد:** الاعتماد يشير للداخل فقط. النطاق لا يعرف قاعدة البيانات ولا Next.js. هذا يجعل الحاسبات وقواعد الميزانية قابلة للاختبار بسرعة وبلا قاعدة بيانات.

## 4. الوحدات (Modules)

### 4.1 خريطة الوحدات

| الوحدة | الميزات | المستوى |
|---|---|---|
| `shared-kernel` | المال، التواريخ، الأخطاء، الأحداث، التدقيق، i18n | L0 |
| `identity` | 3.11 الحسابات والأدوار والمشاركة بالقراءة فقط | L1 |
| `projects` | 3.1 المشاريع والمراحل والمهام والجدول المبسط، 3.15 بوابة الجاهزية | L1 |
| `finance` | 3.2 الميزانية والمصروفات، 3.18 العملة، 3.16 العقود والدفعات والأعمال الإضافية، 3.19 الإدخال السريع | L2 |
| `materials` | 3.3 الحاسبات، 3.9 جدول الكميات، 3.10 سجل الأسعار، 3.23 الجرد الختامي | L2 |
| `quality` | 3.12 + 3.13 + 3.17 (المحرك الموحد)، 3.14 نقاط التوقف الآمنة، 3.23 قائمة تسليم المرحلة | L2 |
| `documents` | 3.4 الوثائق، 3.8 الصور المنظمة | L2 |
| `knowledge` | قاعدة المعرفة الهندسية المراجَعة + 3.6 المساعد | L2 |
| `decisions` | 3.7 مقارنة الاستمرار والتوقف | L3 |
| `trades` | 3.22 حزم أعمال التشطيبات (قوالب سباكة، كهرباء، لياسة، جبس، أرضيات، دهان) | L3 |
| `dashboard` | 3.5 لوحة التحكم (قراءة فقط) | L3 |
| `notifications` | 3.21 التقارير والتنبيهات (يتكامل مع n8n) | L3 |

### 4.2 قاعدة المستويات

الوحدة تعتمد **على المستويات الأدنى فقط**، ولا تعتمد على وحدة من مستواها أو أعلى.

-   L2 لا تستدعي بعضها مباشرة. التواصل الجانبي بين `finance` و`materials` و`quality` يتم **بالأحداث** (القسم 6).
-   L3 تستدعي الواجهات العامة للأدنى (استعلامات وأوامر)، ولا تلمس جداولها أبدًا. مثال: `trades` تطلب من `quality` عبر أمر عام إنشاء قائمة فحص من قالب، ولا تكتب في جدول `checklists`.
-   هذا يمنع الدورات (A تعتمد على B تعتمد على A) التي تقتل التقسيم.

### 4.3 ما تملكه كل وحدة

لكل وحدة: **جداولها، وحالات استخدامها، وواجهتها العامة، وصفحاتها.** لا يقرأ أحد جداول غيره مباشرة.

| الوحدة | الجداول المملوكة (الحالية والمتوقعة) |
|---|---|
| `identity` | `profiles`, `project_members`, `shared_reports` |
| `projects` | `projects`, `phases`, `tasks`, `readiness_gates` |
| `finance` | `budget_categories`, `expenses`, `exchange_rates`, `contracts`, `payments`, `change_orders`, `obligations`, `expected_income` |
| `materials` | `quantity_items`, `purchases`, `price_records`, `stock_counts` |
| `quality` | `checklists`, `checklist_items`, `issues`, `concrete_pours` |
| `documents` | `documents`, `photos` |
| `knowledge` | `kb_entries` (حالة المراجعة ومن راجع) |
| `decisions` | `decision_scenarios` |
| `trades` | `trade_templates` (البند، بنود الفحص، نسبة الهدر، العيوب الشائعة، الدفعة المقترحة، قواعد الترتيب، حالة المراجعة ومن راجع) |
| `notifications` | `notification_log`, `notification_settings` |
| `shared-kernel` | `outbox_events`, `audit_log`, `feature_flags` |

**استثناء وحيد للربط بين الجداول:** مفتاح خارجي (FK) مسموح فقط نحو جداول النواة `projects` و`phases`. أي ربط آخر بين وحدتين يكون **مرجعًا ضعيفًا** (id بلا FK) أو حدثًا.
*مثال:* `purchases.expense_id` يربط `materials` بـ`finance`. يتحول إلى حدث `purchase.recorded` يستهلكه `finance` وينشئ المصروف، فلا تعرف `materials` شيئًا عن جدول المصروفات.

## 5. قواعد العزل (تُفرض آليًا)

| # | القاعدة | كيف تُفرض |
|---|---|---|
| R1 | لا يُستورد من وحدة أخرى إلا ملف `index.ts` العام لها | قاعدة lint (`eslint-plugin-boundaries` أو `dependency-cruiser`) تفشل في CI |
| R2 | الاعتماد نحو الأدنى فقط (القسم 4.2) | نفس القاعدة بمصفوفة اعتماد مسموحة |
| R3 | كل وحدة تصل إلى جداولها فقط | مستودعات (repositories) داخل الوحدة، ومراجعة الكود، واختبار يفحص أسماء الجداول المستخدمة |
| R4 | النطاق (domain) بلا استيراد من البنية التحتية | نفس قاعدة lint |
| R5 | الأرقام المالية والهندسية تُحسب في `domain` فقط | لا حساب في الواجهة ولا في n8n |
| R6 | كل وحدة لها مفتاح تفعيل | `feature_flags`، والواجهة تخفي الوحدة المعطلة |
| R7 | المساعد الذكي وn8n لا يكتبان في البيانات المالية أو الفنية | أدوار قاعدة بيانات بصلاحية قراءة فقط |
| R8 | لا مفاتيح سرية في الكود أو مخططات n8n | متغيرات بيئة محمية |

## 6. التواصل بين الوحدات

| الحاجة | الأسلوب | مثال |
|---|---|---|
| قراءة معلومة من وحدة أدنى | استدعاء مباشر لواجهتها العامة | `finance` تسأل `projects.getProject(id)` |
| تفاعل جانبي بين وحدات L2 | **حدث** عبر Outbox | `expense.created` ← `notifications` تفحص تجاوز الميزانية |
| تجميع بيانات من الجميع للعرض | **عروض قراءة فقط** (views) تملكها `dashboard` | `budget_summary`, `quantity_progress` |

### نمط Outbox

1. الوحدة المنتجة تكتب البيانات **والحدث في نفس المعاملة** (جدول `outbox_events`).
2. عامل (worker) يقرأ الأحداث غير المعالجة ويسلمها للمستهلكين، ثم يعلّمها `processed_at`.
3. المستهلك يجب أن يكون **idempotent** (معالجة الحدث مرتين لا تضر).

**لماذا هذا مهم:** يحمي من فقدان الأحداث عند الأعطال، ويجعل الوحدات منفصلة زمنيًا. والتنفيذ الأبسط الآن: مسار مجدول يستعلم دوريًا. لا نحتاج Kafka ولا غيره.

**أحداث الإصدار الأول:** `expense.created`، `purchase.recorded`، `phase.status_changed`، `quote.expiring`، `checklist.completed`، `issue.opened`، `phase.closing_requested`، `stock.counted`.

**مثال تدفق إغلاق المرحلة (3.23):** لا تستطيع `projects` (L1) أن تعتمد على
`quality` أو `materials` (L2)، لذلك يتم الأمر بالأحداث:
1.  المالك يضغط "إنهاء المرحلة": تضع `projects` الحالة `closing` وتصدر `phase.closing_requested`.
2.  `quality` تنشئ قائمة تسليم المرحلة من القالب، و`materials` تفتح مهمة جرد.
3.  عند الإتمام تصدر `checklist.completed` و`stock.counted`.
4.  `projects` تسجل النتيجة في جدولها `phase_closing_checks`، وتصير المرحلة `done` عند الاكتمال، أو بتأكيد صريح من المالك مع تحذير (القرار D2).

## 7. البنية التحتية والخدمات الطرفية

### 7.1 قاعدة البيانات والعزل بين المشاريع

-   كل جدول يحمل `project_id`، وسياسة RLS على كل جدول.
-   **تعديل مطلوب:** استبدال الاعتماد على `owner_id` وحده بجدول `project_members (project_id, user_id, role)`، والسياسات تستخدم دالة `is_member(project_id)`. بذلك يصبح دور المهندس أو المشاهد إضافة بيانات لا إعادة بناء للصلاحيات.
-   المشاركة بالقراءة فقط (بديل حسابات المهندس والمقاول): جدول `shared_reports` بـ**رمز مخزَّن مُجزَّأ (hash)**، وتاريخ انتهاء، وإمكانية الإلغاء، ونطاق محدود.
-   الاستعلامات تعمل بصلاحية المستخدم نفسه (JWT)، **لا بمفتاح الخدمة (service role)** إلا في مسارات داخلية محدودة ومعروفة.

### 7.2 n8n (الميزة 3.21)

-   يعمل ناقلًا فقط: يستعلم عن **عرض واحد** `weekly_report_v` بدور `reporting_reader` (SELECT على هذا العرض فقط)، ثم يرسل الرسالة.
-   الأرقام تأتي جاهزة من العرض، لا يحسب n8n شيئًا.
-   أي استدعاء من n8n إلى التطبيق يمر عبر مسار داخلي موقَّع (HMAC) ومحدود المعدل.
-   تعطل n8n لا يؤثر على التطبيق، فهو غير مدرج في أي مسار مستخدم متزامن.

### 7.3 الذكاء الاصطناعي (الميزة 3.6)

-   وحدة `knowledge` تضم بوابة (AI gateway) خلف واجهة (port) تُبدَّل فيها المزودات دون لمس بقية النظام.
-   المساعد يقرأ من **مدخلات قاعدة المعرفة المعتمدة فقط** (`status = approved`)، ويذكر المصدر.
-   أدواته استعلامات قراءة فقط، تعمل بصلاحية المستخدم (RLS)، فلا يرى بيانات مشروع غيره.
-   حد للمعدل، ومفتاح إيقاف (flag)، وتسجيل المدخلات والمخرجات للمراجعة.
-   المساعد **لا يصدر حكمًا هندسيًا نهائيًا**، وهذا ملزم بالمبدأين 10 و11 في المرجع.

### 7.4 التخزين

-   الصور والفواتير في مخزن خاص، والوصول عبر روابط موقَّعة قصيرة العمر.
-   التحقق من نوع الملف وحجمه عند الرفع، وضغط الصورة في المتصفح قبله.

## 8. الجوانب العابرة (Cross-cutting)

| الجانب | القرار |
|---|---|
| **المال** | `numeric(14,3)` في القاعدة، ومكتبة عشرية (`decimal.js` أو `big.js`) في الكود. **ممنوع `float`.** العملة الأساسية LYD. |
| **الزمن** | `timestamptz` للأحداث، و`date` للتواريخ التقويمية. العرض بتوقيت Africa/Tripoli. |
| **اللغة** | عربية RTL أساسًا، نصوص في ملفات ترجمة لا في الكود، أرقام وتواريخ بتنسيق موحد. |
| **الأخطاء** | نوع أخطاء موحد في `shared-kernel` (Validation, NotFound, Forbidden, Conflict)، لا استثناءات عامة. |
| **التحقق** | مخططات (Zod) عند كل حدود: النماذج، المسارات، الأحداث. |
| **التدقيق** | `audit_log` لكل تعديل مالي أو فني (من، متى، ماذا تغير). مهم للحجة أمام اللجنة وللثقة. |
| **التزامن (offline)** | إن نُفذت 3.20: عمود `client_op_id` فريد على جداول الكتابة لمنع التكرار عند إعادة الإرسال. تُضاف الأعمدة الآن لأنها رخيصة، ويُؤجل الباقي. |
| **المراقبة** | سجلات مهيكلة بمعرّف طلب، وتتبع أخطاء، وفحص صحة (health check). |
| **مفاتيح التفعيل** | جدول أو ملف تهيئة، بمفتاح لكل وحدة (`quality`, `knowledge`, `offline`...). |

## 10. الاختبار

| المستوى | ماذا يُختبر | الأداة |
|---|---|---|
| وحدة نطاق (unit) | الحاسبات، الميزانية، العملة، حدود التجاوز | Vitest، بلا قاعدة بيانات |
| قاعدة البيانات | سياسات RLS، العروض، القيود | اختبارات SQL (مثل ما جُرّب على PostgreSQL 16)، تُشغَّل في CI |
| حالات الاستخدام | الصلاحيات، المعاملات، الأحداث | اختبارات تكامل على قاعدة محلية |
| حدود المعمارية | R1 إلى R4 | lint/dependency-cruiser |
| واجهة | الرحلات الرئيسية (إدخال مصروف، إنشاء مشروع) | Playwright، قليلة ومركّزة |

**اختبار العزل الإلزامي:** مستخدم ب لا يرى ولا يكتب بيانات مشروع مستخدم أ، على **كل جدول جديد**. يُضاف تلقائيًا لكل ترحيل.
يغطي الاختبار القراءة والإضافة والتعديل والحذف، وكل فحص **يرفع خطأ** (`LEAK`) عند أي تسريب فيفشل CI. طباعة عدد الصفوف وحدها لا تُعد اختبارًا لأنها تنجح دائمًا. والتعديل والحذف يُتحقق منهما بأن عدد الصفوف المتأثرة صفر، لأن RLS يخفي الصفوف ولا يرفض الأمر. وقد ثُبّت ذلك بكسر السياسات عمدًا والتأكد من فشل الاختبار (12 نوفمبر 2026).

## 11. البيئات والنشر

-   **محلي:** Supabase CLI/Docker + بيانات تجريبية.
-   **تجريبي (staging):** مشروع Supabase منفصل لتجربة الترحيلات قبل الإنتاج.
-   **إنتاج:** مشروع آخر. لا تُجرَّب الترحيلات عليه مباشرة.
-   الترحيلات مرقمة ولا تُعدَّل بعد تطبيقها (تُضاف ترحيلات جديدة).
-   **مخاطر الاستضافة المجانية** (تحقق من شروطها الحالية قبل الاعتماد): قد تتوقف قواعد البيانات المجانية عند عدم النشاط، وقد تتغير حدود الطبقات المجانية. الحل: فحص صحة دوري، ونسخة احتياطية يدوية قبل التسليم.

## 12. مسار التوسع (تنظيري، خارج نطاق المشروع)

| المرحلة | متى | ماذا يتغير |
|---|---|---|
| 1 (المشروع) | الآن | Modular monolith + n8n + مزود AI |
| 2 | عند تحميل حقيقي | فصل عامل الأحداث (worker) كخدمة مستقلة، وفصل `notifications` |
| 3 | عند نمو الفريق | فصل `knowledge`/AI كخدمة، ونسخ قراءة لقاعدة البيانات، وتخزين مؤقت |
| 4 | عند الحاجة التجارية | فصل `finance` أو `quality` إذا أصبحت لهما فرق منفصلة |

**لماذا يعمل هذا:** كل مرحلة مجرد نقل وحدة خلف واجهتها العامة وأحداثها الموجودة أصلًا. ولا تُعاد كتابتها.

## 15. ترتيب البناء المعماري

1.  **الأساس:** `shared-kernel`، وإعداد الحدود الآلية في CI، والترحيلات، واختبار RLS.
2.  **L1:** `identity` و`projects`.
3.  **الأولوية 0 و1:** `finance` (مع الإدخال السريع والعملة)، `materials`.
4.  **الأولوية 2:** `quality` (المحرك الموحد) وبوابة الجاهزية.
5.  **بعد المحرك الموحد:** `trades` (السباكة والكهرباء واللياسة أولًا).
6.  **الأولوية 3:** `knowledge` والمساعد، `notifications` + n8n.
7.  **L3:** `dashboard` و`decisions` تُبنى فوق ما سبق.
8.  **الأخيرة:** `documents` المتقدمة وPWA (بقرار المالك، بعد النواة).

**قاعدة:** لا تبدأ وحدة قبل أن تكتمل تبعياتها الأدنى، ولا تُدمج وحدة قبل أن تمر اختبارات العزل.
